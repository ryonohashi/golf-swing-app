# POC-02: リングバッファ

POC-01が通過してから着手する。

## 確かめること

実打と確定したインパクト時刻から遡って、前5秒＋後3秒を1本のクリップとして取り出せるか。そして連続して打った時に破綻しないか。

## 方式

未圧縮フレームを8秒ぶんRAMに保持するのは現実的でない（1080pのraw換算で数GB規模になる）。短い動画チャンクを循環保存し、実打確定後に必要なチャンクを連結する方式を検証する。

```
AVAssetWriter で N秒のチャンクを連続生成し、直近 M 個だけ残して古いものを捨てる
  → 実打確定（動作＋音、POC-01）
    → インパクト時刻を含むチャンクと、その前後の必要なチャンクを連結
      → 1球分のクリップとして確定
```

## 決めること

| 項目 | 備考 |
|---|---|
| チャンク長 | 短いほど切り出しの粒度が上がるが、ファイル数と連結コストが増える。1〜2秒を想定 |
| 保持するチャンク数 | 前5秒＋後3秒を賄える最小数＋余裕 |
| 前後に必要な秒数 | 前5秒は本当に必要か。アドレスからテークバック開始までが入っていればよいなら短縮できる |
| 連続打撃時のクリップ重複の扱い | 下記参照 |
| 後3秒の待機中に次のスイング候補が来た場合の扱い | 下記参照 |

## 連続打撃の扱い

例として、0秒に1球目、4秒に2球目を打った場合を考える。前5秒＋後3秒だと、

- クリップA: -5秒 〜 +3秒
- クリップB: -1秒 〜 +7秒

となり4秒ぶん重複する。

方針の候補:

| 案 | 内容 | 評価 |
|---|---|---|
| A. 重複を許す | それぞれ独立したクリップとして保存する | 実装が最も単純。練習場では次の球をセットする時間があるため8秒以内の連打は稀。容量の増加も限定的 |
| B. 最小間隔を設ける | 前の実打からN秒以内の実打を無視する | 速いテンポで打つ人の球を落とす危険がある |
| C. 切り詰める | クリップAの終端をクリップBのテークバック開始で打ち切る | 実装が複雑で、境界の判定が別の問題になる |

**v1はA（重複を許す）を第一候補とする。** ただし1ショットが2つのピークを生む場合（クラブとボール、続いてクラブとマット）を潰すためのデバウンスは、Aを採る場合でも必須。デバウンス幅はPOC-01で決める。

POCでは実際に速いテンポで打ってみて、Aで実害が出ないかを確認する。

## 測ること

- インパクトから切り出し完了までの所要時間（実打判定にかかる時間を含む）
- 連結したクリップの再生が正常か（シーク、コマ送りが破綻しないか）
- 1クリップあたりのファイルサイズ
- 30〜60分のセッションで生成されるクリップ数と合計容量
- チャンクの循環削除が確実に動くか（ディスクが埋まらないか）

## 合否基準

- インパクトから数秒以内にクリップが確定し、一覧に出ること
- 連続して打った場合もクリップが欠落しないこと
- 60分のセッションでディスク使用量が破綻しないこと

## 決まること

CLAUDE.md の暫定値のうち、クリップの切り出し範囲、リングバッファ長、チャンク長が確定する。
